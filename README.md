# ЯХУ — веб-версия (Docker)

Веб-приложение (браузер вместо iOS) с тем же функционалом, что и в SwiftUI-версии, плюс профиль с фото: дневник питания (сгруппированный по дням — «Сегодня», «Вчера», далее по календарю) с автодополнением из собственной базы блюд, дашборд по калориям/БЖУ/воде с предупреждением о переедании, утренний вес, статистика по неделям и месяцам, награды (ежедневные и еженедельные задания + главная цель) и мягкие напоминания.

**Стек:** один Node.js-сервер без внешних npm-зависимостей и **без каких-либо обращений в интернет** (только встроенные модули, включая собственный мини-парсер xlsx) + статический HTML/CSS/JS фронтенд. Данные хранятся в JSON-файле на сервере (`./data/db.json`, монтируется в контейнер как bind mount — обычный файл в папке проекта, а не Docker-том), поэтому они одинаковые что на компьютере, что на телефоне, и переживают пересборку образа, `git pull`/`git push` и `docker compose down`.

## База блюд (`seed/dishes.xlsx`)

В разделе «Записать еду» поиск работает **только по собственной базе блюд** — никаких обращений в интернет:
1. **1007 популярных домашних блюд и продуктов** — Excel-файл `seed/dishes.xlsx`, равномерно распределённых по 15 категориям (супы, мясо, птица, рыба, гарниры, мучное, выпечка, овощные блюда, салаты, закуски, завтраки, напитки (включая соки), свежие фрукты, ягоды и овощи, а также вода и чай/кофе без сахара) с калориями и БЖУ на 100 г. Помимо конкретных блюд есть и обобщённые позиции на случай, если вы ели просто мясо без гарнира/соуса — «Говядина», «Свинина», «Баранина», «Мясо курицы», «Мясо индейки». Подсказки появляются сразу по мере набора текста (с первой буквы), учитывают частичные и разговорные варианты названий (столбец «Ключевые слова»).
2. **Если ничего не найдено** — можно ввести калорийность на 100 г вручную (БЖУ в этом случае не считаются, только калории).

### Как отредактировать или дополнить базу блюд

1. Откройте `seed/dishes.xlsx` в Excel / Google Sheets / LibreOffice.
2. Добавляйте строки, соблюдая формат столбцов: *Название блюда, Категория, Ключевые слова (для поиска), Калории ккал/100 г, Белки г/100 г, Жиры г/100 г, Углеводы г/100 г, Типичная порция г, Считается как вода (да/нет)*. Последний столбец можно оставить пустым для обычной еды — заполняйте «да» только для чистой воды или несладкого чая/кофе, чтобы их объём автоматически засчитывался в счётчик воды.
3. Пересоберите образ: `docker compose up --build`.

**Важно:** база блюд обновляется в Docker volume **автоматически** при каждом запуске, если вы отредактировали `seed/dishes.xlsx` и пересобрали образ — сервер сам определяет, что версия изменилась (по хэшу файла), и пересеивает базу, не трогая при этом ваши личные правки в `seed/dishes.xlsx`, если вы не меняли его сами (в таком случае ваша правка и станет новой версией при следующей пересборке). Ручные команды для очистки volume больше не нужны. Ваши записи о еде, весе и профиль (`db.json`) при обновлении базы блюд не затрагиваются и никуда не пропадают.

## Дневник питания

Раздел «Дневник» показывает все записи еды, сгруппированные по календарным дням: сегодняшний блок называется **«Сегодня»**, вчерашний — **«Вчера»**, а более ранние дни подписаны как обычная дата («Вторник, 2 сентября», год добавляется, только если запись не за текущий год). Рядом с названием дня — сумма калорий за этот день.

У каждой записи — кнопки ✎ (редактировать) и ✕ (удалить). Редактирование открывает тот же диалог, что и добавление еды, с уже подставленными названием и весом порции: можно поправить только вес (если ошиблись с порцией) — калории и БЖУ пересчитаются автоматически по данным блюда из базы, либо найти в поиске другое блюдо, если ошиблись в названии. Время исходной записи не меняется — правится только сама запись. Сумма калорий и БЖУ за день (на дашборде и в шапке дня в дневнике) сразу пересчитывается по обновлённым данным; если блюдо помечено как вода, связанная запись в счётчике воды тоже корректно пересобирается (или убирается, если после правки блюдо водой быть перестало).

## Дашборд «Сегодня»

Помимо калорий, главный экран показывает суточный прогресс по белкам, жирам и углеводам (ориентировочные цели — 90 / 60 / 220 г, примерная раскладка от 1800 ккал). Если дневная норма калорий (1800 ккал) превышена:
- кольцо и вся карточка «Сегодня» подсвечиваются красным и слегка пульсируют;
- под заголовком появляется баннер «Вы сегодня переели!»;
- один раз показывается всплывающее уведомление в момент превышения порога.

Это не медицинская рекомендация, а мягкий визуальный ориентир — задать точный порог можно, поменяв `DAILY_TARGETS` в `server.js`.

Если один из макросов (белки/жиры/углеводы) уже набран на сегодня, а другой ещё не дотягивает до нормы, под карточкой БЖУ появляется подсказка: «Норма по … уже набрана — добавьте что-то богатое …» с готовым набором блюд из базы (сервер сам подбирает те, что богаты недостающим макросом и не разгоняют уже выполненный, `lib/macro-tip.js`). Нажатие на блюдо сразу открывает знакомый диалог добавления еды с этим блюдом наготове.

## Вода

На дашборде «Сегодня» есть счётчик воды — норма 1500 мл в день, отображается **от обратного** («Осталось выпить N мл»), и заполняется по мере того, как вы пьёте. В блоке «Быстрые действия» есть кнопка **💧 Стакан воды (+250 мл)** — одно нажатие сразу списывает 250 мл с оставшейся нормы.

Кроме того, если вы записываете в «Записать еду» **воду** или **чай/кофе без сахара** (они помечены в базе иконкой 💧), их объём **автоматически** засчитывается в счётчик воды — отдельно вводить их через кнопку не нужно. Обычная еда и напитки с сахаром/молоком на счётчик воды не влияют.

**Автообновление базы блюд.** Раньше при выходе новой версии базы (`seed/dishes.xlsx`) приходилось вручную чистить Docker volume, иначе продолжала использоваться старая версия — из-за этого, например, новые записи «Вода»/«Чай без сахара» могли не подхватываться и не засчитываться в счётчик воды. Теперь это исправлено: сервер при каждом запуске сверяет хэш эталонной базы, «зашитой» в образ, с той, что лежит в volume, и **автоматически пересеивает** её при любом расхождении. Никаких ручных команд для обновления базы больше не требуется.

## Профиль

В правом верхнем углу **каждого раздела** (главная, дневник, прогресс, награды) — кнопка-аватарка (нажмите, чтобы открыть профиль; кнопка «Назад» возвращает туда, откуда вы пришли). Раздел «Профиль»:
- **Фото** — JPEG или PNG, до 5 МБ (проверяется и в браузере, и на сервере). Можно заменить или удалить.
- **Поля**: имя, фамилия, год рождения, возраст (считается автоматически из года рождения — отдельно вводить не нужно, поле только для отображения), пол (мужской/женский), желаемый конечный вес.
- **Желаемый конечный вес синхронизирован с целью** приложения — именно это значение используется в карточке «Цель на год» на главном экране и в главной цели «Пушинка!» в разделе «Награды», отдельного дублирующего поля нет.
- **Напоминания** — здесь же, под личными данными, два независимых переключателя: «Пить воду» и «Сделать разминку». У каждого свой интервал, настраиваемый шагом по 5 минут (кнопки −/+, диапазон 5–240 мин), и свой выключатель — можно включить только воду, только разминку, обе сразу или ни одной.

Фото хранится как base64 в том же `db.json`, что и остальные данные — отдельного файлового хранилища не потребовалось.

## Мотивационная фраза дня

Вверху главного экрана — тёплая мотивационная фраза про заботу о себе и путь к цели. Она меняется **раз в сутки** (одна и та же фраза весь день, следующая — завтра), берётся из списка ~30 фраз в `server.js` (константа `MOTIVATIONAL_PHRASES`) — можно дополнять или менять список под себя.

## Награды

Раздел «Награды» состоит из четырёх блоков:

- **Главная цель — «Пушинка!»** Присваивается один раз, когда последний записанный вес становится меньше или равен желаемому весу из профиля. Дальше остаётся полученной, даже если вес потом немного вырастет.
- **Ежедневные задания** — «Выпита норма воды» и «Записан вес» засчитываются **сразу**, в момент выполнения условия (выпили норму воды / отметили вес сегодня) — ждать конца дня не нужно, повторное превышение нормы или повторная запись веса в тот же день счётчик не задваивают. «Не превышено калорий», наоборот, можно узнать только постфактум и засчитывается **в конце дня**, при переходе на следующие календарные сутки — иначе один поздний перебор по калориям всё равно засчитался бы как «норма не превышена». Все три требуют, чтобы за день реально была запись — пустой день не засчитывается автоматически. Карточка показывает статус на сегодня и счётчик «×N» — сколько раз всего было выполнено это задание за всё время.
- **Еженедельные награды** — «Слежу за калориями» (норма калорий не была превышена **все 7 дней** календарной недели, с понедельника по воскресенье) и «Любитель воды» (норма воды выполнена все 7 дней). Подводятся итогом **в конце недели**; карточка показывает, сколько дней текущей недели уже выполнено (например, «4 из 7»), и общий счётчик «×N».
- **Вехи** — разовые достижения общего характера («Первый шаг», «Забота о себе», «Спокойная неделя»), не привязанные к конкретному дню.

Прогресс всех наград хранится на сервере (`db.json`, поле `achievements`) и переживает перезапуск — подведение итогов идёт автоматически при каждом обращении к `/api/state` (см. `lib/achievements.js`), досчитывая все полностью завершившиеся дни/недели, даже если сервер какое-то время не запускался.

## Прогресс: календарные недели/месяцы с историей

В разделе «Прогресс» у графиков «Вес», «Калории» (со статистикой Б/Ж/У под ним) и «Вода» есть переключатель **Неделя / Месяц** и стрелки **‹ ›** для пролистывания истории — переключаются независимо для каждого графика:
- **Неделя** — календарная неделя, с понедельника по воскресенье, по дням.
- **Месяц** — календарный месяц, с 1-го по последнее число (например, 1–31 августа); данные внутри месяца показаны 7-дневными блоками, чтобы график оставался читаемым, а не превращался в частокол из ~30 узких столбиков.

**История ведётся с момента первой записи.** Кнопка «‹» пролистывает назад — вплоть до недели/месяца, в котором была сделана самая первая запись (дальше кнопка блокируется). Кнопка «›» листает вперёд, но не дальше текущей недели/месяца — в будущее заглянуть нельзя.

**Вес** показывает только дни/недели, где реально была запись (в отличие от калорий и воды, для веса пропуск дня не равен «0 кг» — такой день просто не рисуется столбиком). Отображается с точностью до десятых («69,8», а не округлённые «70»).

**Статистика Б/Ж/У под графиком калорий** — суммарные белки/жиры/углеводы за тот же период, что выбран в переключателе (сумма за неделю или сумма за месяц), обновляется вместе с графиком.

**Анимация.** При переключении периода или пролистывании столбики графика заполняются слева направо с лёгким плавным замедлением в конце (ease-out), а не появляются мгновенно.

Агрегация считается на клиенте из полной истории записей, отдельных серверных эндпоинтов для этого не потребовалось.

## Хостинг, который "засыпает" (сброс прогресса на бесплатных тарифах)

Многие бесплатные хостинги (Render, Railway, Fly.io, Cyclic и похожие) "усыпляют" контейнер при бездействии, а когда он снова просыпается — это часто не тот же самый контейнер, а свежесозданный из образа, с чистой файловой системой. Файл `data/db.json`, в который сервер пишет прогресс, при этом бесследно пропадает — именно поэтому после "просыпания" всё обнуляется. Это не баг в коде, а особенность эфемерного диска на таких тарифах: обычный локальный файл там в принципе не может пережить пересоздание контейнера.

Решение — **бесплатная синхронизация с Upstash Redis** (внешнее хранилище именно для такого случая: 256 МБ и 500 000 команд в месяц бесплатно, без банковской карты). Она уже встроена в проект (`lib/remote-sync.js`) и включается двумя переменными окружения — без них всё работает как раньше (только локальный файл).

**Настройка (5 минут, один раз):**
1. Зарегистрируйтесь на [upstash.com](https://upstash.com) (можно через GitHub-аккаунт) и создайте базу — Console → Redis → Create Database. Регион можно любой, тип — Regional, бесплатного тарифа достаточно с большим запасом.
2. На странице базы найдите блок **REST API** (иногда подписан "Connect your database" → вкладка "REST API" или пример на Node.js) — там будут показаны `UPSTASH_REDIS_REST_URL` и `UPSTASH_REDIS_REST_TOKEN`.
3. Добавьте эти два значения в переменные окружения вашего хостинга (в настройках сервиса на самом хостинге — там, где обычно задают `PORT` и подобное) под ровно такими же именами:
   - `UPSTASH_REDIS_REST_URL`
   - `UPSTASH_REDIS_REST_TOKEN`
4. Перезапустите деплой. В логах сервера при старте должна появиться строка `Состояние восстановлено из Upstash Redis...` (при первом запуске — `В Upstash Redis пока нет сохранённого состояния...`, это нормально, база ещё пуста).

Дальше при каждом сохранении (добавили еду, воду, вес и т.д.) состояние дополнительно уходит в Upstash в фоне, не замедляя ответ. При следующем "просыпании" контейнера сервер сначала подтянет оттуда последнее состояние — и только потом начнёт отвечать на запросы, так что прогресс не потеряется.

Локальный `data/db.json` при этом никуда не делся — он по-прежнему пишется первым (быстро и синхронно) и остаётся рабочим резервным вариантом, если Upstash на секунду недоступен; на хостинге с постоянным диском (свой VPS, Docker с volume/bind mount) можно вообще не подключать Upstash — там эта проблема изначально не возникает.

Если нужен свой отдельный ключ (например, тестовое и боевое окружение делят один аккаунт Upstash) — задайте `UPSTASH_REDIS_KEY` (по умолчанию `yahu-app-state`).

Полный список переменных окружения, которые понимает сервер, с описанием — в `.env.example` (это шаблон-подсказка, не настоящие секреты; сам файл `.env` с реальными значениями в git не попадает, см. `.gitignore`).

### Как проверить, что подключение реально работает

Не нужно гадать по логам хостинга — прямо в приложении есть самодиагностика:
- Откройте `/api/health` в браузере (например, `https://ваш-сайт.onrender.com/api/health`) — там видно, настроен ли Upstash (`configured`), успешно ли прошло восстановление при последнем старте (`lastLoadOk`) и последнее сохранение (`lastSaveOk`), а если что-то не так — текст ошибки в `lastLoadError`/`lastSaveError`.
- То же самое, но красиво — в разделе **Профиль → 🛠 Инструмент разработчика** (пароль `B201190aU`), карточка вверху журнала.

Частые причины, почему не работает, даже если переменные заданы:
- **Вставлена не та строка.** В Upstash на странице базы есть несколько вкладок подключения — нужна именно **REST API** (`UPSTASH_REDIS_REST_URL` начинается с `https://...upstash.io`, `UPSTASH_REDIS_REST_TOKEN` — длинная строка). Строка для `redis-cli` (начинается с `redis://` и содержит `:6379`) для REST не подходит — сервер теперь явно это обнаруживает и пишет об этом в `/api/health`.
- **Переменные заданы не для того сервиса/окружения.** На Render переменные окружения задаются в настройках конкретного Web Service (Environment → Add Environment Variable) и требуют **Manual Deploy** (или автоматически передеплоятся, в зависимости от настроек) — просто сохранить переменную недостаточно, нужен передеплой, чтобы сервис перезапустился уже с ней.
- **Опечатка/лишний пробел** при копировании токена — скопируйте значения ещё раз целиком, без пробелов в начале/конце.

Само по себе сообщение хостинга вида *"Your free instance will spin down with inactivity, which can delay requests by 50 seconds or more"* — это ожидаемое поведение бесплатного тарифа (задержку первого запроса после сна ничем, кроме платного тарифа, не убрать), и **не свидетельствует о проблеме** — оно означает лишь то, что после долгого бездействия первый заход может подождать до ~50 секунд, пока хостинг поднимет контейнер. С Upstash после этого ожидания данные будут на месте.

### Обходной путь: не давать сервису засыпать вовсе

Если хочется вообще избежать задержки в 50+ секунд (не только защитить данные, но и убрать саму паузу при заходе) — можно не дать Render усыпить сервис: он засыпает только при **полном отсутствии входящих запросов** 15 минут подряд, значит, достаточно самим присылать лёгкий запрос почаще. Ни один "самопинг" изнутри самого сервера не поможет (когда контейнер остановлен, весь код внутри него, включая любые таймеры, тоже не выполняется) — пинговать нужно **снаружи**.

**Вариант 1 — GitHub Actions (уже в проекте, ничего дополнительно регистрировать не нужно).**
В `.github/workflows/keep-alive.yml` есть готовый workflow, который раз в 10 минут дёргает `/api/health` вашего сайта (лёгкий эндпоинт, ничего не пишет). Настройка — одна переменная:
1. В репозитории на GitHub: **Settings → Secrets and variables → Actions → вкладка Variables → New repository variable**.
2. Имя: `SITE_URL`, значение — адрес сайта без слэша на конце, например `https://yahu.onrender.com`.
3. Готово — сработает по расписанию само. Проверить сразу, не дожидаясь расписания: вкладка **Actions** → **Keep-alive ping** → **Run workflow**.

**Вариант 2 — внешний бесплатный мониторинг** (если не хочется полагаться на GitHub Actions): [UptimeRobot](https://uptimerobot.com) или [cron-job.org](https://cron-job.org) — регистрация, добавить HTTP(s)-монитор на `https://ваш-сайт.onrender.com/api/health` с интервалом 5 минут, бесплатно.

**Важный нюанс с часами Render:** бесплатный тариф даёт 750 часов в месяц на весь workspace, а в месяце максимум 744 часа — то есть держать **один** сервис постоянно включённым весь месяц укладывается в лимит с небольшим запасом. Но если в том же workspace на Render есть и другие бесплатные сервисы — они делят один и тот же лимит в 750 часов, и суммарно легко его превысить, тогда Render приостановит бесплатные сервисы до начала следующего месяца. Если сервис только один — переживать не о чем.

Также учтите: GitHub автоматически отключает scheduled workflows, если в репозитории 60 дней подряд не было ни одного коммита — если вы продолжаете время от времени пушить изменения, это не проблема; если нет — можно вручную перезапустить через **Run workflow** или настроить внешний мониторинг (вариант 2) вместо/вместе с GitHub Actions.

## Запуск

Нужен установленный [Docker Desktop](https://www.docker.com/products/docker-desktop/).

1. Откройте терминал в этой папке (там, где `docker-compose.yml`).
2. Выполните:
   ```
   docker compose up --build
   ```
3. Откройте в браузере на компьютере: **http://localhost:3000**

Первый запуск соберёт образ (нужен интернет для скачивания `node:20-alpine`), дальше запускается мгновенно.

Остановить: `Ctrl+C`, затем при необходимости `docker compose down` (данные в `./data` останутся на диске — это обычная папка проекта, а не Docker-том).

## Установка на iPhone (PWA — иконка на главном экране)

**Про `.apk`/`.ipa`:** нативный `.apk` (Android) или `.ipa` (iOS) — это не то, что можно собрать «в облаке» без специфичных для платформы инструментов. Для `.ipa` конкретно нужен Mac с Xcode и Apple ID (это требование самой Apple, а не ограничение инструмента сборки). Вместо этого приложение сделано устанавливаемым как **PWA (Progressive Web App)** — даёт иконку на главном экране, полноэкранный режим без адресной строки браузера, и не требует ни Mac, ни App Store, ни денег.

Телефон и компьютер должны быть в одной Wi-Fi сети.

1. Узнайте локальный IP компьютера, на котором запущен Docker:
   - **Windows**: `ipconfig` → строка «IPv4-адрес» (обычно `192.168.х.х`)
   - **macOS**: `ipconfig getifaddr en0` (или Настройки → Wi-Fi → значок ⓘ)
2. На iPhone откройте **Safari** (обязательно Safari, не Chrome — только в нём работает «Добавить на экран Домой» с полноценной PWA-установкой) и перейдите на:
   ```
   http://<IP-компьютера>:3000
   ```
   например `http://192.168.1.42:3000`
3. Нажмите кнопку «Поделиться» (квадрат со стрелкой вверх, снизу экрана) → **«На экран Домой»** → «Добавить».
4. На главном экране появится иконка «ЯХУ» с фирменным зелёным листом — открывается на весь экран, без адресной строки, как обычное приложение.

Если телефон не подключается — вероятная причина в брандмауэре Windows. Быстрая проверка/фикс в PowerShell (от администратора):
```powershell
netsh advfirewall firewall add rule name="YAHU Docker 3000" dir=in action=allow protocol=TCP localport=3000
```
Также убедитесь, что тип сети в Windows — «Частная», а не «Публичная» (Параметры → Сеть и Интернет → Wi-Fi → тип профиля): Docker Desktop по умолчанию блокирует входящие подключения для публичных сетей.

## Про напоминания

Настоящие push-уведомления в PWA на iOS Safari сильно ограничены Apple, а системный `Notification API` в браузере на многих устройствах требует HTTPS и явного разрешения — этого нельзя гарантировать для локального личного приложения. Поэтому основной канал напоминаний «Пить воду» и «Сделать разминку» (в разделе «Профиль», каждое — вкл/выкл + интервал с шагом 5 минут) сделан так, чтобы работать гарантированно, пока открыта вкладка приложения:
- **крупное всплывающее окно** с именем пользователя из профиля («Иван, пора выпить воды») — это нативный `<dialog>`, поднимающийся в top layer браузера, поэтому оно перекрывает содержимое **любого раздела**, в котором пользователь сейчас находится;
- **короткий двухтональный звуковой сигнал** («аккуратный бип»), сгенерированный на лету через Web Audio API — работает без аудиофайлов и без HTTPS.

Системное уведомление (`Notification API`) добавляется как бонус-канал сверху — на случай, если браузер и разрешения это позволяют и вкладка свёрнута.

Отсчёт до следующего напоминания не сбрасывается посторонними действиями в приложении (добавили еду, сохранили профиль и т.п.) — таймер перезапускается, только если пользователь реально изменил включение или интервал.

## Мгновенная загрузка при обновлении страницы

Раньше каждое обновление страницы (F5, pull-to-refresh, повторный визит) означало 1.5–2 секунды пустого экрана, пока браузер грузил файлы приложения и ждал ответа сервера с данными. Теперь это устранено на двух независимых уровнях:

- **Оболочка приложения** (HTML/JS/иконки) кэшируется service worker'ом (`public/sw.js`) — при повторных заходах отдаётся мгновенно из кэша, а свежая версия молча подгружается в фоне на следующий раз (stale-while-revalidate). Дополнительно расставлены заголовки `Cache-Control` на сервере (`lib/http-utils.js`) — подстраховка на случай, если service worker ещё не активен (самый первый визит).
- **Данные** (калории, БЖУ, вода, дневник и т.д.) кэшируются в `localStorage` браузера (`public/app.js`, `loadState()`): при каждом обновлении страницы последний известный снимок данных отображается **сразу**, не дожидаясь ответа сервера, а как только реальный ответ приходит — экран тихо обновляется актуальными цифрами. Так что вместо пустого экрана на 1.5–2 секунды пользователь сразу видит интерфейс с (почти наверняка) правильными данными. Фото профиля в этот кэш не попадает (может весить несколько мегабайт и не нужно для мгновенного отображения цифр на главном экране).

`/api/state` и другие ответы API помечены `Cache-Control: no-store` — актуальность данных обеспечивает именно описанный выше механизм на уровне приложения, а не браузерный HTTP-кэш.

## Обновление жестом (потяни вниз)

На главном экране (и на любом другом, если он прокручен в самый верх) можно потянуть экран вниз пальцем — появится кружок-индикатор, а при отпускании после небольшого порога происходит обычная полная перезагрузка страницы, как кнопка «Обновить» в браузере. Это компенсирует то, что у мобильных браузеров (включая Safari на iPhone) нет системного жеста pull-to-refresh для обычных веб-страниц — такое поведение есть по умолчанию только у Chrome на Android.

## Отклик на нажатия

Любая кнопка и переключатель в приложении при нажатии слегка "сжимаются" (визуальный отклик) и сопровождаются коротким тихим "тик"-звуком — оба эффекта генерируются на лету (CSS-анимация + Web Audio API), без картинок/аудиофайлов. Как и со звуком напоминаний, браузер разрешает звук только после реального клика пользователя, поэтому самый первый тап по любой кнопке на странице заодно и "включает" звук для всех последующих.

## Перенос в GitHub / работа в локальной директории

Проект уже содержит `.gitignore` (исключает `data/*` — там только личные рантайм-данные пользователя, `.gitkeep` оставлен). Если раньше папка `D:\App\yahu-web` git-репозиторием не была, первый перенос делается так (Windows, PowerShell или Git Bash):

```
cd D:\App\yahu-web
git init
git add .
git commit -m "Первый коммит: ЯХУ веб-версия"
```

Дальше — создать пустой репозиторий на github.com (без README/лицензии, чтобы не было конфликта веток) и привязать его как remote:

```
git branch -M main
git remote add origin https://github.com/<ваш-логин>/<название-репозитория>.git
git push -u origin main
```

После этого для каждого следующего изменения:

```
git add .
git commit -m "Краткое описание изменений"
git push
```

### Почему прогресс (дни, статистика, награды) больше не теряется

- `data/` целиком в `.gitignore` — `git add .` его никогда не подхватит, а значит `git push`/`git pull`/`git checkout` физически не могут его затронуть.
- В `docker-compose.yml` данные подключены как **bind mount** (`./data:/app/data`) — это обычная папка проекта на диске, а не именованный Docker-том. `docker compose up --build` (пересборка образа после обновления кода) её не трогает; том пропал бы только если явно выполнить `docker compose down -v` или почистить Docker командой вроде `docker system prune --volumes` — обычных `git`/`docker compose up`/`down` (без `-v`) для этого недостаточно.
- Запись на диск атомарная (через временный файл + переименование) — прерванная запись (сбой питания, принудительная остановка контейнера) не может испортить `db.json` наполовину.
- Если `db.json` всё же почему-то окажется повреждён, сервер не сотрёт прогресс молча: рядом появится резервная копия `db.json.corrupted-<время>`, из которой данные можно восстановить вручную.

Если у вас ещё не настроен Git локально — понадобится [Git для Windows](https://git-scm.com/download/win) и аккаунт на GitHub с включённой двухфакторной аутентификацией (GitHub больше не принимает пароль напрямую для `git push` — либо личный токен (PAT), либо GitHub Desktop/SSH-ключ).

## Инструмент разработчика (журнал действий)

Внизу экрана «Профиль» есть неприметная ссылка **🛠 Инструмент разработчика** — открывает диалог с паролем (`B201190aU`, задан в `server.js` константой `DEV_TOOL_PASSWORD`, либо переменной окружения `DEV_TOOL_PASSWORD`). Пароль проверяется на сервере (`POST /api/devtools/auth`), поэтому его нельзя подсмотреть, просто открыв исходный код страницы в браузере — только сам файл `server.js`. Неверный пароль доступ **не даёт** (показывается ошибка, экран не открывается).

После входа наверху показывается статус синхронизации с Upstash (подключён/не подключён/ошибка — см. раздел «Хостинг, который засыпает»), а ниже — журнал последних действий в приложении: переходы между разделами, добавление/редактирование/удаление еды, запись веса, добавление воды, включение/выключение и изменение интервала напоминаний, сохранение профиля, загрузка/удаление фото, срабатывание pull-to-refresh, а также сами попытки входа в этот раздел (успешные и неуспешные). Хранится на сервере в `db.json` (поле `devLog`, не более 500 последних записей — старые вытесняются), с кнопками «Обновить» и «Очистить журнал».
